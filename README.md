# JMComic 下载（MaiBot 插件）

把 [JMComic-Crawler-Python](https://github.com/hect0x7/JMComic-Crawler-Python)
的下载能力接进 [MaiBot](https://github.com/Mai-with-u/MaiBot)。群里发一个车号，
机器人后台下载并落盘，再把图片用**合并转发**（一条聊天记录）发回会话。

| 项目 | 值 |
| --- | --- |
| 插件 ID | `github.winincorce-a11y.mai-jmcomic` |
| 插件版本 | `1.1.0` |
| 宿主版本区间 | `1.3.0` ~ `1.3.99` |
| SDK 区间 | `2.19.0` ~ `2.99.99` |
| Python 依赖 | `jmcomic >= 2.7,<3` |
| 声明能力 | `send.text`、`send.image`、`send.forward` |

> 本插件只是 `jmcomic` 的聊天入口，**不内置、不再分发任何内容**。
> 下载行为与内容合法性由部署者自行负责。

---

## 一、功能概览

| 功能 | 说明 |
| --- | --- |
| 整本下载 | 按车号下载整本（含全部章节） |
| 单章下载 | 只下载指定章节 |
| 详情查询 | 标题、作者、页数、章节数、标签；并标注是否 AI 作品 |
| 搜索 | /jm search 关键词 [页码]：站内搜索，服务端真分页，结果以聊天记录发送 |
| 作品系列搜索 | /jm series 作品名 [页码]：按原作/系列搜（如 蔚蓝档案），结果与网页端同量级 |
| 作者搜索 | /jm author 作者名 [页码]：按作者/画师搜 |
| 登场人物搜索 | /jm actor 角色名 [页码]：按角色搜（建议用日文原名） |
| 标签搜索 | `/jm tag 标签1、标签2 [页码]`：按真实 tag 过滤（AND 语义），结果分页、以聊天记录发送 |
| 任务管理 | 查看进度、取消任务 |
| 异步执行 | 下载在后台线程跑，命令立即返回，不阻塞聊天 |
| 发送策略 | 合并转发 / 逐张发送 / 只下载；可限制张数与单图大小 |
| AI 过滤 | 按禁漫 tag 与标题识别 AI 作品，可只过滤搜索或连带下载 |
| 限流 | 每日配额、用户冷却、并发/排队上限、会话黑白名单 |
| LLM 工具 | `jmcomic_search`、`jmcomic_download` 供规划器调用 |

## 二、安装

1. 把整个 `mai-jmcomic` 目录放进 MaiBot 的 `plugins/` 下。

   > **目录名建议保持 `mai-jmcomic`，不要改成 `jmcomic`。**
   > PyPI 的包名就是 `jmcomic`，目录同名会在 `sys.path` 上遮蔽真实模块，导致
   > `import jmcomic` 拿到插件目录而不是库。

2. 在 WebUI 插件管理里启用「JMComic 下载」。

3. 安装 Python 依赖。首次启用时 Host 会读取 `_manifest.json` 里的
   `python_package` 声明并尝试用 `uv` 自动安装；若自动安装被禁用，手动执行：

   ```bash
   uv pip install "jmcomic>=2.7,<3"
   # 或
   pip install -r requirements.txt
   ```

   `jmcomic` 会一并带上 `curl_cffi`、`pillow`、`pycryptodome`、`pyyaml`、
   `commonx`，体积较大，首次安装需要一点时间。

4. 插件首次加载会在插件目录生成 `config.toml`，按需修改。

## 三、命令

所有命令都走同一个主命令（前缀支持 `/jm`、`/jmcomic`、`/禁漫`，
也兼容全角斜杠 `／`，不区分大小写）：

```text
/jm                         显示帮助
/jm 350234                  下载整本并发送
/jm p123456                 只下载单章
/jm info 350234             查看详情
/jm search 关键词           站内搜索第 1 页
/jm search 关键词 2         站内搜索第 2 页
/jm series 蔚蓝档案         按作品系列搜索第 1 页
/jm series 蔚蓝档案 2       按作品系列搜索第 2 页
/jm author ぽんこっちゃん    按作者/画师搜索第 1 页
/jm actor アロナ            按登场人物搜索第 1 页
/jm tag 标签1、标签2        按标签搜索第 1 页（AND 语义）
/jm tag 标签1、标签2 2      按标签搜索第 2 页
/jm status                  查看当前会话的任务
/jm cancel 1a2b3c4d         取消指定任务（按前缀匹配任务号）
/jm cancel all              取消当前会话全部任务
```

另外注册了一条**裸车号**命令，直接发这些也能触发下载：

```text
JM123456      jm-123456      jm_123456      禁漫123456     车号：123456
```

### 3.1 子命令别名

除主写法外，还接受以下别名（不区分大小写）：

| 子命令 | 可用别名 |
| --- | --- |
| 帮助 | `help` `h` `?` `？` `帮助` `-h` `--help` |
| 搜索 | `search` `s` `搜` `搜索` `查` `找` |
| 标签 | `tag` `t` `标签` `標籤` `tagsearch` |
| 详情 | `info` `i` `详情` `信息` |
| 状态 | `status` `st` `状态` `任务` `队列` |
| 取消 | `cancel` `c` `取消` `停止` |
| 下载 | `download` `dl` `下载` `get` |

**没匹配到任何子命令时，整段参数会被当成搜索关键词。**
所以 `/jm 不知什么关键词` 等价于 `/jm search 不知什么关键词`，
而 `/jm 350234` 因为解析出了车号，走的是下载。

### 3.2 车号识别规则

从文本里按以下顺序识别，命中即止：

| 写法 | 示例 | 结果 |
| --- | --- | --- |
| 前缀 + 数字 | `JM350234`、`jm-123456`、`禁漫 123456`、`车号：123456` | 整本 |
| 链接 | `https://18comic.vip/album/350234/` | 整本 |
| 链接（章节） | `https://18comic.vip/photo/123456` | 单章 |
| 单章标记 | `p123456`、`photo-654321` | 单章 |
| 裸数字 | `123456` | 整本 |

范围限制：数字必须 **4~8 位**且落在 `1000`~`9999999` 之间；
裸数字要求 **5~8 位**，避免把年份（`2024`）、长串（`1234567890`）、
`QQ123456789` 这类内容误判成车号。

## 四、配置

配置文件为插件目录下的 `config.toml`，WebUI 会按模型生成中文表单
（每个字段都有中文名与填写说明）。以下默认值取自 `1.1.0`。

### `[plugin]`

| 字段 | 默认 | 说明 |
| --- | --- | --- |
| `enabled` | `true` | 关闭后所有 `/jm` 命令只回复「已停用」 |
| `config_version` | `1.0.0` | 配置版本，由插件维护，界面上只读 |

### `[download]`

| 字段 | 默认 | 说明 |
| --- | --- | --- |
| `base_dir` | 空 | 下载根目录。**空则用 `<插件数据目录>/downloads`**；相对路径也基于该目录 |
| `dir_rule` | `Bd_Pname` | jmcomic 目录规则：`Bd`=根目录，`Pname`=章节名 |
| `threads` | `8` | 单章图片下载并发数，范围 1~32 |
| `image_suffix` | 空 | 强制图片后缀（如 `.jpg`）；空则保留原格式 |
| `client_impl` | `api` | `api` 或 `html`。`api` 更快更省流量 |
| `domains` | 空 | 自定义域名，逗号分隔；空则用 jmcomic 内置域名池 |
| `proxy` | 空 | 代理地址（如 `http://127.0.0.1:7890`）；空则跟随系统代理 |
| `decode` | `true` | 是否解码图片；关闭后保存的是站点原始文件 |
| `retry_times` | `3` | 请求重试次数，范围 0~10 |
| `delete_after_send` | `false` | 发送成功后删除本地文件 |

> 插件数据目录由 Host 分配，通常是 `data/plugins/github.winincorce-a11y.mai-jmcomic/`。
> 实际落盘路径形如 `<base_dir>/JM<车号>/<章节名>/00001.jpg`。

### `[send]`

| 字段 | 默认 | 说明 |
| --- | --- | --- |
| `mode` | `forward` | `forward`=合并转发；`image`=逐张发送；`none`=只下载不发送 |
| `max_images` | `0` | 单次最多发送张数。**`0`=不限制** |
| `forward_batch` | `0` | 单条聊天记录最多放多少张。**`0`=不限制** |
| `forward_retry` | `2` | 合并转发失败后的重试次数，范围 0~5（总尝试 = 1 + 该值） |
| `forward_fallback` | `none` | 重试仍失败时：`none`=不补发；`image`=逐张补发 |
| `image_interval_ms` | `300` | 逐张发送的间隔（毫秒） |
| `max_image_mb` | `8.0` | 单张图片大小上限（MB），超过则跳过该图 |

**关于 `0` = 不限制**

`max_images` 与 `forward_batch` 都是「0 即不限制」。两者默认都是 `0`，
所以整部作品默认会合并成**一条**聊天记录一口气发完。

真正会触发拆分的只有一个硬约束：**单条合并转发的 base64 总量**。
Runner 的 RPC 单帧上限是 16MB，插件按 **12MB** 预算控制（预留 msgpack
包装与字段开销）。实测 50 张 JPG 约 7.6MB，可一条放下；超过才会拆成多条，
并在日志里写明拆了几条。

### `[limits]`

| 字段 | 默认 | 说明 |
| --- | --- | --- |
| `daily_per_chat` | `5` | 每个群/私聊每日下载次数，`0` 不限制 |
| `max_concurrent` | `1` | 同时执行的任务数，范围 1~5 |
| `max_pending` | `10` | 排队任务上限，超过则拒绝新请求 |
| `cooldown_seconds` | `10` | 同一用户两次下载的最短间隔（秒），`0` 不冷却 |
| `allowed_chats` | 空 | 白名单：只允许这些群号/QQ号使用；空=不限制 |
| `blocked_chats` | 空 | 黑名单：禁止这些群号/QQ号使用；**优先级高于白名单** |

**黑白名单判定顺序：先黑后白。**

```text
请求进来
  ├─ 命中黑名单？            → 拒绝（即使同时写在白名单里也不放行）
  ├─ 配了白名单且不在其中？  → 拒绝
  └─ 否则放行
```

两个字段都支持中英文逗号与空格分隔，群号或 QQ 号任一命中即生效。
拦截范围是整个插件的所有入口：`/jm` 全部子命令、裸车号命令、
以及两个 LLM 工具。

两种拒绝的提示文案不同，便于排查：

- 命中黑名单 → `⛔ 当前会话已被拉黑，无法使用 JM 功能。`
- 不在白名单 → `⛔ 当前会话不在白名单内，没有使用 JM 的功能权限。`

### `[search]`

| 字段 | 默认 | 说明 |
| --- | --- | --- |
| `display` | `10` | 每页展示条数，同时是翻页步长（范围 1~30），各种搜索共用 |
| `tag_candidates` | `200` | **多标签**搜索时最多核对多少条候选（范围 1~600），单标签不受影响 |

**搜索是服务端分页（80 条/页）。**

`main_tag` 是搜索模式开关，插件把它包装成 5 条命令：

| 命令 | `main_tag` | 搜什么 |
| --- | --- | --- |
| `/jm search` | 0 | 站内全字段（标题 + 作者 + 标签一起匹配） |
| `/jm series` | 1 | **作品系列**（原作/企划，如 蔚蓝档案） |
| `/jm author` | 2 | **作者 / 画师** |
| `/jm tag` | 3 | **标签**（必须是精确标签名） |
| `/jm actor` | 4 | **登场人物 / 角色** |

实测**这五种模式都真的支持 `page`**——同一个关键词翻页返回完全不同的作品，
`total` / `page_count` 也是服务端给的真实值（`蔚蓝档案`：站内 7935 条 /
794 页，作品系列 6865 条 / 687 页）。

服务端一页 80 条，而群里 `display` 默认 10 条，所以插件把服务端页缓存起来
再在本地切：**连翻 8 页只用一次请求**，第 9 页才取下一个服务端页。

> 五条命令共用同一套分页逻辑，唯一区别是 `main_tag`；缓存也按模式分开，
> 同一个词在 `search` 与 `series` 下各存各的，不会互相串结果。

**所有搜索结果都以「聊天记录」发出，带封面、标题不截断。**

一页 10 条结果如果一条条发出去，群里几秒就刷满了。所以 `/jm search`、
`/jm series`、`/jm author`、`/jm actor`、`/jm tag` 五条命令的结果都打包成
**一条合并转发**（一个气泡，点开是完整列表），连「没有搜到 / 页码越界」
这类提示也一样。

每条结果发成「封面图 + 完整标题」两个节点：

```text
[封面缩略图]
JM1486387 [欶瀾漢化組] [ちぃずオレ] ダイビング部ご奉仕漫畫【前編】 (ブルーアーカイブ) [中國翻譯]
```

- **标题不截断**：搜索就是为了看清是哪一本，长标题原样显示。
- **封面**用禁漫列表缩略图（`/media/albums/<车号>_3x4.jpg`），由车号直接
  拼出，不需要先查详情。实测单张 60~90KB，10 张预热后约 10 秒、冷启动
  约 30 秒。
- 封面缓存在插件数据目录的 `covers/` 下，**同一车号不会重复下载**，
  翻页与重复搜索基本是秒出。
- 封面是锦上添花：单张失败、超时（60 秒总预算）或关掉 `[search].cover`
  时只是少几张图，列表照常发；`cover_count`（默认 10，最大 30）控制最多配几张。

页头是标题与页码，页尾是翻页命令：

```text
🔎 按作品系列「蔚蓝档案」第 1/687 页，共 6865 条（本页 1-10）
[图] JM1486387 [欶瀾漢化組] [ちぃずオレ] ダイビング部ご奉仕漫畫【前編】 ...
...
发送 /jm 车号 下载；下一页：/jm series 蔚蓝档案 2
```

- 合并转发被平台拒绝（重试 `forward_retry` 次后仍失败）时，自动退回
  **一条普通文本**，保证用户至少能看到结果。
- 发给 LLM 工具（`jmcomic_search`）的仍是纯文本，不带封面、不进聊天记录。

### 按作品系列搜索 `/jm series`

```text
/jm series 蔚蓝档案         第 1 页
/jm series 蔚蓝档案 2       第 2 页
```

「作品系列」就是禁漫的**原作**（那部动画/游戏/漫画本身），对应接口的
`main_tag=1`。它和「标签」不是一回事：

| 搜什么 | 命令 | 蔚蓝档案的命中 |
| --- | --- | --- |
| 作品系列（原作） | `/jm series 蔚蓝档案` | **6865 条**（687 页） |
| 站内搜索（全字段） | `/jm search 蔚蓝档案` | 7935 条（794 页） |
| 标签（必须是精确标签名） | `/jm tag 蔚藍檔案` | 9 条 |

所以找某个企划/游戏的本子时优先用 `/jm series`；直接搜关键词（`/jm search`）
会把标题、作者、标签一起匹配，范围更大但也更杂。

实测（`/jm series 蔚蓝档案`，每页 10 条）：第 1 页 39s（含首次域名/凭据
初始化，站点抖动时更久）、第 2 页 0.0s（同一批 80 条里）、第 500 页 25s
（要取第 63 个服务端页）。

### 按作者搜索 `/jm author`

```text
/jm author ぽんこっちゃん      第 1 页
/jm author ぽんこっちゃん 2    第 2 页
```

别名：`author` `artist` `artists` `作者` `画师` `畫師` `绘师`。

`main_tag=2`，同样是服务端分页。实测 `ぽんこっちゃん` 有 102 条（11 页）。
非常适合「追某个画师」，结果里会混着该画师参与的多部作品。

### 按登场人物搜索 `/jm actor`

```text
/jm actor アロナ               第 1 页
/jm actor 砂狼シロコ 2         第 2 页
```

别名：`actor` `character` `char` `登场人物` `人物` `角色` `登場人物`。

`main_tag=4`，服务端按**角色**过滤（不是标题里出现过这个名字，而是禁漫给
作品打的角色标记），所以结果比站内搜索精准得多。

> **重要：要用日文原名。** 禁漫的角色词条基本是日文写法，中文译名命中率很低：
>
> | 输入 | 命中 |
> | --- | --- |
> | `砂狼シロコ`（全名） | 10 条 |
> | `シロコ`（只给名字） | 12 条 |
> | `アリス` | 33 条 |
> | `白洲アロナ`（中文姓 + 日文名） | **0 条** |
> | `アロナ` | 2 条 |
>
> 所以查不到时先换成日文名；不确定全名就把姓去掉，只留名。

### 按标签搜索 `/jm tag`

```text
/jm tag 巨乳               单个标签，第 1 页
/jm tag 巨乳、NTR          多个标签（同时满足，AND 语义）
/jm tag 巨乳 3             第 3 页
```

标签支持 `、`、`,`、`，` 与空格分隔，不区分大小写、忽略全半角差异；
多标签按「包含匹配」比较（`汉化` 能命中 `中文汉化`；反之不成立）。
页码写在标签后面（前面要有空格），它不含空格，所以不会和标签混淆。

**单标签走服务端搜索，翻一页只发一个请求。**

禁漫搜索接口的 `main_tag` 参数其实是「搜什么」的模式开关：

| `main_tag` | 含义 | 实测 |
| --- | --- | --- |
| 1 | 搜作品名（`search_work`） | `巨乳` 只有 18 部（标题里带这个词的），`page` 无效 |
| 2 | 搜作者 | — |
| 3 | **搜标签**（`search_tag`） | `巨乳` 每页 80 条、`page` 真的生效、可翻 125 页 |
| 4 | 搜登场角色 | — |

所以 `/jm tag 巨乳` 直接就是服务端标签搜索：`page_count = ceil(total / 80)`，
`total` 是服务端给的真实条数。代价为零——一次 HTTP 请求拿 80 条，本地再按
`display` 切成 8 页（每页 10 条），**连翻 8 页都只用一次请求**。

实测（`巨乳`，每页 10 条）：第 1 页 23s（含首次域名/凭据初始化）、
第 2 页 0.0s（同一批 80 条里）、第 9 页 1.1s、第 1000 页 1.2s。

> `total` 有**封顶**：实测任何热门标签都返回 `10000`，对应 125 个服务端页。
> 达到封顶时结果写成「共命中 10000+ 部」，表示「至少这么多」。

**多标签要逐条核对，因为服务端做不到 AND。**

服务端的 `search_query` 是多词「或」匹配：实测同时搜 `巨乳 汉化` 会返回
只带「汉化」甚至只带「禁漫漢化組」的作品。所以多标签的做法是：

```text
/jm tag 巨乳、NTR
   ├─ 先各查一次，看每个标签各有多少部作品（1 次请求/标签）
   ├─ 挑**结果最少**的那个标签当候选流（命中率最高、最省请求）
   ├─ 按它的服务端分页一批批取候选（80 条/页）
   └─ 逐条查详情核对，凑够这一页（10 个命中）就停
```

探测进度会缓存 10 分钟：翻到第 2 页是**接着上次的位置继续核对**，
不会重头再查，也不会一上来把几百条候选全扒完。

多标签的时间代价：

| 场景 | 实测 |
| --- | --- |
| 候选流 120 条、每 6 条命中 1 条 | 凑够第 1 页（10 个命中）核对了 60 条 |
| 每轮核对 | 20 条一批，约 20 秒 |
| 上限 | `tag_candidates`（默认 200，最大 600） |

**AI 过滤与 tag 补全：**

服务端标签搜索的列表**不返回每条作品的 tag**。只有开了 `[filter].enabled`
时，插件才会对**本页这 10 部**并发查一轮详情把 tag 补上（供 AI 判定用），
并且给了 8 秒总预算——到点就走，补不到的条目就当没有 tag（AI 判定退回
只看标题），绝不为了补 tag 把翻页拖住。

**结果的呈现方式：**

一页结果打包成**一条合并转发（聊天记录）**，不再一条条刷屏：

```text
JM1207803 (C85) [エイトビート (伊藤エイト)] 沖田家のおもてなし ...
```

页头给页码与命中数，页尾给翻页命令：

```text
🏷 标签「巨乳」第 1/1000 页｜共命中 10000+ 部（第 1-10 部）
发送 /jm 车号 下载；下一页：/jm tag 巨乳 2
```

- 合并转发被平台拒绝（重试 `forward_retry` 次后仍失败）时，
  会自动退回**一条普通文本**，保证用户至少能看到结果。
- 页码越界时明确告知「共命中 N 部，没有第 X 页（共 M 页）」并给出回第 1 页的命令。
- 多标签没核对完时，页头会写「已命中 N 部……后面还有候选没核对」，
  而不是假装总数已知。
- 同一页结果也会走 AI 过滤，被隐藏的条数写在页头。

### `[filter]` — AI 作品过滤

| 字段 | 默认 | 说明 |
| --- | --- | --- |
| `enabled` | `false` | 是否启用 AI 过滤 |
| `scope` | `all` | `search`=仅搜索；`search_download`=搜索+下载；`all`=搜索+下载+详情 |
| `keep_in_search` | `false` | 搜索结果里是否仍展示 AI 作品（`true` 只标注不隐藏） |
| `operator_bypass` | `true` | 管理员（本地操作员）是否可跳过过滤强制下载 |

**判定依据**（纯离线，不联网、不调用模型）：

1. **详情 tag**（最可靠）：匹配 `AI`、`AI上色`、`AI生成`、`AI着色`、
   `AI作画`、`AI繪`/`AI绘`、`aigenerated` 等，大小写不敏感；
   已排除 `Raid`、`aid` 这类误判。
2. **标题 / 描述**：同上规则，作为拿不到 tag 时的兜底。

**两段判定的强度不同，这是已知限制：**

| 场景 | 有无 tag | 判定强度 |
| --- | --- | --- |
| 搜索结果 | ❌ 搜索接口不返回 tag | 只能按标题判断，较宽松 |
| 下载 / 详情 | ✅ 会先查一次详情 | 按完整 tag 判断，较严格 |

也就是说：某作品标题不含 AI 字样、只有 tag 里有 `AI上色` 时，它可能正常
出现在搜索结果里，但真正 `/jm` 下载时会被拦下。

**缓存与失败处理**

- AI 判定按**车号**缓存（上限 500 条，满了整体清空），不会重复查详情。
- 下载前的这次详情查询有 **30 秒超时**。查询失败时**放行不拦**
  （记一条 warning），把错误留给下载阶段正常上报，避免因网络抖动误拦。
- `scope=search` 时下载不受影响；`scope=search_download` 时详情查询不受影响。

## 五、运行机制

### 5.1 一次下载的完整流程

```text
/jm 350234
   │
   ├─ 校验（任一不通过即回复并结束）
   │    ├─ 插件启用？           [plugin].enabled
   │    ├─ jmcomic 可用？       启动时已探测
   │    ├─ AI 过滤？            命中且非管理员绕过 → 拒绝
   │    ├─ 黑白名单？           先黑后白
   │    ├─ stream_id 存在？
   │    ├─ 同会话同车号在跑？   避免重复任务
   │    ├─ 排队数未超限？       [limits].max_pending
   │    ├─ 用户冷却已过？       [limits].cooldown_seconds
   │    └─ 今日配额未用完？     [limits].daily_per_chat
   │
   ├─ 创建 Job → 立即回复「任务 xxxxxxxx 已排队」
   │
   └─ 后台任务（受 max_concurrent 信号量约束）
        ├─ asyncio.to_thread(jmcomic.download_*)   ← 不阻塞事件循环
        ├─ 每 1.5s 轮询目录统计图片数（仅用于 status 进度）
        ├─ 读取图片 → base64 → send.forward / send.image
        └─ 回复「下载 N 张，发送 M 张，耗时 …，任务 xxxx」
```

### 5.2 发送与「未确认回执」

QQ / SnowLuma 经常出现**消息已经进了聊天记录，但适配器没拿到回执**的情况。
插件的处理是：

1. 合并转发失败时按 `forward_retry` 重试（间隔 1.5s）；
2. 重试仍失败，按 `forward_fallback` 决定：

   | 值 | 行为 | 适用 |
   | --- | --- | --- |
   | `none`（默认） | 不补发，任务仍算成功，把这批张数计入「未确认」 | 推荐，图片不会跑到聊天记录外面 |
   | `image` | 逐张补发 | 只在确认平台真的没收到时用；可能造成重复 |

完成汇报会显式区分：

```text
✅ JM1453342《书名》
作者：xxx ｜ 63 页 ｜ 2 章
下载 50 张，发送 20 张（合并转发）
ℹ️ 其中 20 张平台未返回回执，通常已在聊天记录里，未重复补发
耗时 12 秒，任务 b04ea6cf
```

### 5.3 取消与配额

- 取消会同时调用 jmcomic 的 `DownloadControl.cancel()` 并取消 asyncio task。
- **普通成员只能取消自己发起的任务；管理员可取消当前会话的任意任务。**
- 任务失败、取消、或被中止时会**退回配额**；成功则不退。
- 配额存内存 + `<插件数据目录>/quota.json`，按自然日滚动。

### 5.4 其它行为

- 同一车号重复下载会命中 jmcomic 的 `cache`，不会重新拉图。
- 任务记录只保留最近 60 条，避免常驻内存无限增长。
- 单张图片原始字节超过 `_MAX_IMAGE_BYTES`（8MB，硬上限）会被跳过，
  因为 base64 后可能顶到 RPC 帧上限。

## 七、开发与测试

自带一套**不联网**的单测，用一个假的 `jmcomic` 模块验证完整链路
（下载、发送、失败回退、取消、限流、过滤、Schema 等）。

```bash
python -m unittest discover -s tests -v
```

- 需要 `maibot-plugin-sdk` 可导入，**不需要**安装 `jmcomic` 本体。
- 当前共 **172 个用例**，全部通过。

### 目录结构

```text
mai-jmcomic/
├── _manifest.json     # 插件清单：ID、版本区间、jmcomic 依赖、能力声明
├── plugin.py          # SDK 入口：配置模型、命令、任务、发送、过滤、限流
├── jm_service.py      # jmcomic 薄封装：option 构造 / 详情 / 搜索 / 下载
├── jm_core.py         # 纯逻辑：车号解析、AI 识别、任务状态、配额、格式化
├── config.toml        # 运行时生成（不要提交）
├── requirements.txt   # 手动安装依赖用
└── tests/             # 假 jmcomic + 假 ctx 的单测
```

### 分层约定

- `jm_core.py`：**零依赖**（不 import `maibot_sdk`、不 import `jmcomic`），
  纯函数，最适合单测。
- `jm_service.py`：只与 `jmcomic` 打交道，所有同步阻塞调用都在这里，
  由 `plugin.py` 放进 `asyncio.to_thread`。
- `plugin.py`：只做 SDK 接线（配置、命令、工具、发送、调度）。

## 八、常见问题

**Q：日志提示 `jmcomic 不可用`**

运行插件的 Python 环境里 `import jmcomic` 失败。先确认装在了正确的环境
（MaiBot 的宿主/运行环境，不是系统 Python），再检查代理与域名是否可达。
装好后在 WebUI 重载插件即可。

**Q：命令执行成功，但群里只看到「正在查询」**

多半是别的插件拦了出站消息。本插件已配合 `talk-rate` 修复过这个问题
（命令回复豁免从一次性 5 秒改为 120 秒滑动窗口）；若仍出现，检查日志里
`send_service.before_send` 是否被某个 Hook abort，以及插件自身的
`文本消息未送达` 警告。

**Q：下载了一大堆图，但只发出来一部分**

按顺序检查：

1. `max_images` 是否被设成了非 0 的小数值；
2. 是否超过 `max_image_mb`（超限的图会被跳过）；
3. 是否超过 12MB 单条预算被拆成多条（看日志「拆成 N 条聊天记录」）；
4. 是否命中 `forward_fallback=none` 的未确认回执（看完成汇报里的
   「其中 N 张平台未返回回执」）。

**Q：搜索翻页翻不动 / 每页内容一样**

已修复。旧版假设搜索接口忽略 `page`，改成「只取一页 + 本地切片」，结果总数
被卡在 80 条。现在实测 `main_tag=0/1/2/3/4` 五种模式**都支持真翻页**，
所以改为服务端分页：`total` / 页数都是真实值（`蔚蓝档案` 作品系列 6865 条）。
若仍异常，确认插件版本 ≥ `1.4.0`。

**Q：搜「蔚蓝档案」结果很少 / 和网页端差很多**

用 `/jm series 蔚蓝档案`。`/jm search` 是站内搜索（标题+作者+标签一起匹配），
`/jm series` 才是按**作品系列（原作）**搜：实测同一个词，站内 7935 条、
作品系列 6865 条，而 `/jm tag 蔚藍檔案` 只有 9 条（标签必须是精确标签名）。
找某个企划/游戏的本子，优先 `/jm series`。

**Q：`/jm actor 角色名` 搜不到东西**

角色词条是**日文写法**，中文译名基本查不到。实测同一个角色：
`砂狼シロコ` 10 条、`シロコ` 12 条、`アリス` 33 条，而 `白洲アロナ`
（中文姓 + 日文名）**0 条**、`アロナ` 2 条。查不到就换日文名，
或者去掉姓只留名再试。

**Q：怎么找某个画师的全部作品**

`/jm author 画师名`（别名 `artist` / `画师` / `作者`）。这个画师参与过的
作品都会列出来，包括他只是作画、原作是别人的那些。实测 `ぽんこっちゃん`
有 102 条。画师名同样建议用**日文原名**（禁漫词条以日文为主）。

**Q：标签搜索要等多久**

看标签数量：

- **单标签**：翻一页就是一次服务端请求。首屏 5~25 秒（含首次域名/凭据初始化），
  之后大多 1~2 秒；同一批 80 条里的 8 页连翻是 0 秒。
- **多标签**：必须逐条查详情核对（服务端只支持单标签），每批 20 条约 20 秒，
  凑够一页就停；进度缓存 10 分钟，翻下一页是接着核对。

**Q：标签搜索怎么翻页 / 能翻出多少**

`/jm tag 巨乳 2`、`/jm tag 巨乳 3` …… 每页 `display` 条（默认 10）。
单标签能翻到服务端的全部结果（热门标签上限 10000 部 = 1000 页），
页尾会直接给出上一页/下一页的命令。

**Q：标签搜索的结果数量怎么才算「和网页端一样」**

单标签就是服务端搜索，所以和网页端同一份数据、同样的翻页深度
（网页端每页 80 条，这里每页 10 条，能翻到同样的第 10000 部）。
多标签服务端只做「或」匹配，插件用逐条核对来保证 AND，因此只会覆盖
「最稀有那个标签」的候选范围，数量少于网页端的模糊搜索——这是语义更严格
的代价，页头会如实写「已命中 N 部，后面还有候选没核对」。

**Q：搜索结果为什么是转发的聊天记录**

一页 10 条结果如果一条条发出去会刷屏，所以五种搜索（站内 / 作品系列 /
作者 / 登场人物 / 标签）的结果统一打包成一条合并转发，一个气泡点开就是
完整列表，复制车号也方便。连「没有搜到」这种提示也走聊天记录。
若平台拒绝合并转发，插件会自动退回一条普通文本，不会什么都不发。

**Q：搜索太慢 / 只想要文字**

封面是主要开销：默认每页下 10 张缩略图。把 [search].cover 关掉就只发
文字，或者把 cover_count 调小。封面下载过会缓存在插件数据目录的
covers/ 里，同一车号不会再下一次，所以翻页和重复搜索很快。

**Q：封面没出来 / 少了几张**

封面下载是「尽力而为」：单张失败、超过 60 秒总预算、或车号对应的缩略图
本身不存在时，就只发标题。列表本身不会因此失败。如果整页都没图，先确认
[search].cover 是 	rue、cover_count 不是 0，再看日志里有没有
「封面下载失败」。

**Q：想一次发完整部作品**

默认就是。`max_images` 与 `forward_batch` 都为 `0`（不限制），
整部作品会合并成一条聊天记录；只有单条 base64 超过 12MB 才会拆。
若之前手动改过这两个值，改回 `0` 即可。
